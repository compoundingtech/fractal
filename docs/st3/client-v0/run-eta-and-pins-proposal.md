# Proposal: run ETA and person pins

Status: client-v0 contract proposal for the web sidebar; no implementation or
wire behavior change yet. Both additions are additive and optional: older
daemons omit them.

## Current behavior and intended measure

The web sidebar needs run and step timing, a remaining-duration estimate for
an open run, and an ordered pin list for the principal. Timing comes from
existing folds, with no new storage. Pins reuse arrangements rather than
changing folder placement.

The current contract defines `MissionRunSummary`, `MissionStep`, and
`ArrangementKey` in `docs/st3/client-v0/schemas/client-v0.schema.json`.
The presentation rules in `docs/clients/ui-contract.md` serve display state
computed once on the published card. An ETA instead belongs to one open run:
a mission row reads its current open run. It does not belong on
`MissionPresentation`.

## Negotiation and wire shape

### Run and step timing

As a prerequisite, add these nullable timestamp fields to `MissionRunSummary`
and `MissionStep`:

```text
started_at: Timestamp | null
completed_at: Timestamp | null
```

Run start is run creation, and run end is the terminal state claim
(`outcome.at`). Step start is the `work.claimed` claim, and step end is the
terminal `work.*` claim. The existing `STEP_TIMING_KINDS` fold and
`step_timing_events` in `crates/fractal-store/src/store.rs` read the step timing
claims. The daemon serves the new timing fields with the same bound as today's
run enrichment: open runs plus the latest finished run.

### Run ETA

Add an optional `eta` field to `MissionRunSummary`:

```text
eta?: {
  remaining_low_ms: integer,    // p25 of the remaining duration
  remaining_high_ms: integer,   // p75 of the remaining duration
  basis: { method: "per-step" | "critical-path", samples: integer },
  as_of: Timestamp
} | null
```

The ETA is served as remaining durations plus `as_of`, not as absolute
timestamps. Absolute times become wrong as soon as a run pauses. With
durations, a client can show "over by 10m" and can show a pause honestly.
While the principal holds the run, a client may show "waiting on you" instead
of the ETA. The server still serves the value.

`null` means one of two things: some remaining step has zero completed
samples, or the run is finished. Older daemons omit the field. `as_of` is the
publication cut that produced the value.

## Capture and delivery across layers

ETA computation runs on the server. The time basis is the wall time of each
step, excluding only the periods when a person holds the step (a decision or
a person wait). Queueing and agent waits count, because the reader experiences
them as real delay.

For each remaining step, the daemon takes p25 and p75 of that duration from
the completed runs of the same step path under the current definition hash.
If dependencies are declared (step `blockers`), the daemon sums along the
critical path, and `method` is `critical-path`. Otherwise the daemon sums over
the remaining steps, and `method` is `per-step`.

`samples` is the smallest sample count among the remaining steps. With 1 or 2
samples the value is still served, so a client can say "(1 prior run)".

## Contract surface and consumer coordination

### Person pin set

The pins live in a second reserved arrangement per person:
`arrangement/person/NAME/00000000-0000-7000-8000-000000000002`. A proposed
`PINS_ARRANGEMENT_UUID` constant sits next to `SIDEBAR_ARRANGEMENT_UUID`.
The existing constant is generated from `constants.sidebar_arrangement_uuid`
in `docs/st3/client-v0/schemas/operations.json`; the Sidebar identity rules
are in `docs/clients/ui-contract.md`.

Its placements, `{folder: root, key: ArrangementKey}`, form the ordered pin
list:

- The pin set reuses the existing `arrangement.edited` claims,
  last-writer-wins resolution and sync, with no `ArrangementBody` version
  change and no new operation tag.
- Pins are separate from folder placement. Pinning or unpinning a subject
  never touches the Sidebar arrangement.
- The subjects allowed are the same as for placement: agents, missions,
  machines and docs/resources. PTY and session subjects are refused.
- Ordering keys are `ArrangementKey` values (base-62 fractional keys),
  generated by clients, as for the Sidebar. The canonical key definition is
  in `docs/st3/client-v0/schemas/client-v0.schema.json`.
- There is no separate pin limit. The existing arrangement limits apply.

### Open contract questions

- Is the reserved second arrangement acceptable for pins, or are
  `subject.pin`/`subject.unpin` registers in a version 2 Sidebar body preferred?
- Should `eta` sit on `MissionRunSummary` (as proposed) or on `Mission`?
- Should both features be always-on optional fields (as proposed, following
  recent mission timing fields), or gated by a capability version?

### Implementation order

Each implementation PR is at most 300 lines:

1. Serve run and step `started_at`/`completed_at`.
2. Add the reserved Pins arrangement constant, its docs and a fixture.
3. Add the ETA fold and cache, and serve `eta`.

## Verification required for implementation

- Check timing against run creation, terminal `outcome.at`, and the step
  timing claims, preserving the open-runs-plus-latest-finished-run bound.
- Check per-step and critical-path estimates, the current-definition-hash
  sample set, and exclusion of person-held time without excluding queueing
  or agent waits. Check the smallest sample count, including 1 or 2 samples,
  and `null` for a zero-sample remaining step or a finished run.
- Check remaining durations and the publication-cut `as_of`, including the
  display of a paused or overdue run and omission by older daemons.
- Check ordered pin placements, last-writer-wins sync, permitted subjects,
  refusal of PTY and session subjects, and existing arrangement limits.
  Pinning and unpinning must leave Sidebar folder placement unchanged.
